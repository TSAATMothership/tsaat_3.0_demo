# Database lifecycle and data contracts

## Authoritative artifacts

The current storage contract is inventory v2. The fresh schema, common eight-week JSON evidence bundle and SQL/JSON readers/writers evolve together. See [provider contracts](data-providers.md) and [retirement upgrade and recovery](feature-retirement.md).

- `Database Schema/database-schema.sql` is destructive fresh-install DDL; never apply it to an existing operational database.
- Published migrations 001–032 remain unchanged. Migration 033 is the explicit forward retirement upgrade for existing installations through 032.
- `Database Schema/data/database-build-manifest.json` selects current reference data and the fresh-only additions 025, 031 and 032. Fresh setup does not replay retired analytics migrations.
- `Database Schema/retired-storage-v2.json` enumerates removed tables, routines, references and fields. The [generated catalogue](generated/database-catalogue.md) documents source, not deployed state.

## Retained data model

Snapshot-aware keys relate managed networks, ICT systems, assets, environments and membership tables. Include snapshot keys in every relationship. Endpoint OS/patch level, network OS/patch state, installed software, vulnerabilities and discovery evidence support retained Explorers, Insights and CMDB details. Service/capability membership and directed CI dependency observations support Topology. Lifecycle dates and identifiers remain when used by inventory/CMDB; retiring an analytics page does not discard shared inventory.

Discovery coverage rules/settings and persona revisions are the remaining shared configuration. CMDB definitions/mappings remain configurable for asset and model CIs. Current discovery evaluation is available in both providers. Findings, KPI/SPI evaluation/configuration/history, risk/priority matrices, tasking/report definitions, network target-state assets and server patch analytics are removed. OS major-version comparison fields are removed; Explorer patch level remains.

SQL marks version 2 in `tsaat.storage_schema_version`; JSON uses `store.json.schemaVersion`. Both require the upgraded store. Compilation never migrates an existing installation.

## One-command database setup

After `npm ci --offline`, run `npm run setup:database` under the Windows identity that will run the app. Interactive setup first asks `Is the SQL Server endpoint localhost\SQLEXPRESS? [Y/n]`. Yes/Enter selects local SQLEXPRESS; No asks for a nonempty endpoint such as `tcp:server,port` or `server\instance`. For local SQLEXPRESS, setup reads the instance's enabled TCP configuration and selects its configured static or assigned dynamic port when available, including a loopback-only listener. If inspection is unavailable, it retains the named endpoint. It never changes instance protocols or starts SQL Browser.

Interactive setup prepares **TSAATDB**, including when an existing DB_config names a different database. Enter a new database username, or an existing SQL login when replacing the database (default `tsaat_app` or the previously saved SQL username), a hidden password and its confirmation. Use the existing password when reusing a login. Then select the administrator connection: current Windows account by default, or a separate SQL administrator username/password. The administrator must be a SQL Server sysadmin; the application login receives no server roles. SQL Server must already allow SQL Server and Windows authentication (mixed mode). Setup does not install SQL Server, enable protocols, change authentication mode or restart services.

`setup:database` now explicitly disables SSL for the administrator/bootstrap connection and the saved application connection. There are no SSL/certificate questions in this workflow. DB_config remains encrypted at rest using Windows DPAPI; administrator credentials are never persisted. A server configured to force encryption can still require TLS; setup does not change server policy. Database Settings is removed; its compatibility APIs return 410 and do not read/write DB_config or test connections. Configuration-only tools retain TLS support, including Strict. The CLI change supersedes the setup portion of [ADR 0016](adr/0016-complete-database-setup.md); see [ADR 0017](adr/0017-dedicated-database-login.md).

The endpoint and credential questions are shown on every interactive setup, even with an existing DB_config. Answer No to enter a different endpoint. If a named instance cannot be reached, enter its configured `tcp:server,port` endpoint. Check administrator credentials and mixed mode when connection/login preflight fails. Passwords follow the server's password policy; setup accepts up to 128 characters without line breaks or semicolons and trims surrounding whitespace, consistent with DB_config. Passwords are not printed or passed as process arguments.

For a missing database, setup confirms the target, creates it with a race-safe CREATE, applies the inventory-v2 base schema and only the fresh-schema additions listed in the build manifest, streams local reference JSON and eight sample snapshots through the administrator connection, and populates the existing sample entity/CVE details. No SQL Server file shares are needed. The data is bundled demonstration material. After schema validation, setup creates the login and matching database user in a transaction. The user receives `db_datareader`, `db_datawriter`, `EXECUTE` on the `tsaat` schema and `VIEW DEFINITION` in this database. It receives neither `db_owner` nor server administrator roles. Login creation enforces the server password policy, with password expiration disabled for this application account.

The final connection/schema/snapshot checks use the new application login; SSL diagnostics are skipped because SSL is disabled. Only after these checks succeed does setup save DPAPI-encrypted DB_config. Run `npm run dev:sql`, or `npm run build:sql` followed by `npm run start:sql` for a compiled app. Runtime SQL passwords are sent through the child process's `SQLCMDPASSWORD` environment. Failed SQL authentication no longer automatically retries as the Windows runtime account; the legacy fallback requires explicit `TSAAT_SQL_TRUSTED_FALLBACK=true`.

For an existing database, setup now **deletes and replaces it** after checking the administrator and application login. Interactive setup displays the server/database, explains that all data/settings will be lost and active sessions disconnected, and requires typing the exact database name. Enter, Yes, or another name cancels before deletion. No automatic backup is created; make your own backup before confirming if existing data is needed. Setup rechecks the observed database ID/creation timestamp before dropping it from a master connection, then invokes the guarded bootstrap against the now-missing name. System databases cannot be replaced. Other databases are untouched. This behavior is defined in [ADR 0018](adr/0018-replace-database-during-setup.md).

A setup-managed login is recognized by the `TSAAT_SETUP_LOGIN` property and matching SID. When replacing an existing database, setup also accepts the selected existing SQL login without that marker or a database-user mapping, including after an interrupted bootstrap. It verifies the existing password and authenticated SID before deletion, rejects server-role membership, and carries that exact SID through the run to reconnect the login. If the login is removed or replaced, reattachment fails instead of creating or adopting a different identity. Setup never resets passwords, drops server logins, changes other database mappings or remaps conflicting users. A different new username is also supported. See [ADR 0030](adr/0030-reuse-login-for-database-replacement.md).

Login/user changes are transactional, but dropping and rebuilding a database is not: a later failure cannot recover the removed data. Failed builds remain for inspection and DB_config is not overwritten. Restore your own backup to recover the old data. If bootstrap stopped before the login was reattached, retry the repaired setup with that login's existing password; the partial database still requires exact-name replacement acknowledgement. When the selected database is missing, unmarked existing logins remain refused.

Unattended setup requires `TSAAT_DB_CONFIG_ASSUME_YES=true`, `TSAAT_SQL_SERVER`, `TSAAT_SQL_USER` and `TSAAT_SQL_PASSWORD` for new configuration. `TSAAT_APP_DATABASE` defaults to TSAATDB; explicit alternate names support disposable validation. **Replacing an existing database additionally requires `TSAAT_DB_REPLACE_EXISTING` equal to the exact selected database name**; assume-yes alone cannot delete it. The administrator defaults to Windows authentication; supply both `TSAAT_SQL_ADMIN_USER` and `TSAAT_SQL_ADMIN_PASSWORD` for SQL administrator authentication. SSL is disabled by this workflow. An existing readable SQL/no-SSL DB_config takes precedence on reruns. Existing Windows/SSL configurations require an interactive run or an isolated `-- -DbConfigPath <path>`; unattended runs refuse to silently convert them. Use process environment variables for secrets. The app itself reads DB_config in its working directory.

The lower-level `npm run db:bootstrap -- -DatabaseName TSAAT_UI3_Dev` remains available with encrypted certificate-trust defaults and refuses an existing database. For strict validation, invoke the PowerShell script with `-TrustServerCertificate:$false`. It does not create an application login or save DB_config; use `setup:database` for the complete workflow. Direct `ensure-db-config.ps1` without `-SetupDatabase` remains configuration-only and retains its authentication/TLS options for compatibility.

Repository JSON is demo/test material, not an export of the running database. Database cleanup is validated using isolated restored/fresh databases; the original database is not implicitly rebuilt or migrated.

Fresh guarded bootstrap also applies the reviewed CVE inventory population after sample import. This is limited to the new disposable database and is separate from additive migration 028; existing/operational databases are never populated by an application build.

Inventory-v2 bootstrap does not invoke the legacy server-patch population: `server_patch_observation` is retired. If an older setup stopped with that missing-table error, the imported database may remain but the new DB_config was not saved. Inspect the selected target before retrying the repaired `setup:database`; replacing it still requires its exact database-name acknowledgement and deletes its contents. This setup repair changes no stored fields and requires no new SQL or JSON migration. Existing pre-v2 stores still need the explicit paired upgrade below.

For lower-level `SqlServerFiles` loading, stage the reference files and snapshots selected by the current build manifest. File-read preflight selects its reference probe from that manifest; the retired `reference-versions.json` is not required. Ordinary setup continues to stream local JSON using `ClientPayload`.


## Existing installation upgrade

Stop application writers and take a verified backup of the explicitly selected target. Review migration prerequisites and custom dependencies before applying 033 with its target-specific acknowledgement. Do not replay earlier migrations or use setup:database to upgrade. See the [paired SQL/JSON commands and rollback procedure](feature-retirement.md).

Existing stores predating 032 need their missing applicable forward schema upgrades reviewed first. Demonstration-only population scripts are never operational migrations. Preserve saved transport/certificate policy; failures must not downgrade it. Validate retained inventory, scopes, dates, CMDB, discovery/persona settings and exports after upgrading.

## No-SQL relationship

Use the common loader facades for feature code. JSON snapshots, settings and CMDB references belong to the selected absolute store; source fixtures are sample material, not a live SQL export. Setup/build/start initialize only missing stores and refuse incompatible existing stores. The explicit JSON v2 migration backs up and projects every active/history snapshot and persona revision. SQL exports and JSON imports accept only the retained inventory contract. Never overwrite installed data with sample fixtures.
