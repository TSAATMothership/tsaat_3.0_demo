# Database lifecycle and data contracts

For the shared eight-week bundle and a non-resetting update to existing sample databases/stores, see [sample evidence](sample-evidence.md). SQL append takes a verified native backup, uses the fresh loader's field mapping in a transaction, and preserves existing dates, settings and reference data. This data update does not reapply the base schema.

## Authoritative artifacts

- `Database Schema/database-schema.sql`: fresh-install objects, constraints and routines. It drops/recreates existing schema objects and is destructive on an existing TSAAT database.
- `Database Schema/migrations/`: ordered upgrades through 031; retain history for existing installations.
- `Database Schema/data/`: reference/configuration JSON and build manifest.
- `Database Schema/loaders/`: import and validation. The low-level loader creates schema and imports demo data, requiring a new database by default; it is not a production migration runner. Explicitly disabling its new-database guard is destructive and is never appropriate for an operational database.
- [ERD](../Database%20Schema/ERD.md), schema description and data mapping: domain relationships and source mappings.
- [Generated catalogue](generated/database-catalogue.md): base-schema fields, foreign keys, routines and migration inventory. It documents source, not the actual deployed schema.

## Data model

Migration 029 adds server_patch_observation with one nullable evidence record per snapshot/server, a composite asset FK, nonnegative update counts and bounded deployment statuses. It is separate from existing network-device asset_patch_state. The shared SQL payload, JSON import and loader support all fields; old JSON records remain compatible. Upgrade before running the new full SQL loader. A separately opted-in sample population script and guarded NEW database bootstrap supply labelled examples without replacing observations. See [patch data contract and rollback](patch-management-explorer.md).

Snapshot-aware keys relate dataset_snapshot, managed_network, ict_system, asset and environment/membership tables. Include snapshot keys in joins. Assets have OS, network OS, patch, software, vulnerability and discovery evidence. Findings retain workflow, timestamps, scope, priority, severity and evidence. Service/mission links drive impact analysis.

KPI/SPI definitions, calculations, SPI parameters, outcome text, report bindings and tasking templates are SQL configuration. KPI-1 checks presence of an ICT-system ATO; KPI-2 uses DIIS registration. Network header scope resolves systems using selected infrastructure and deduplicates them. SPI applicability and risk/priority matrices remain configurable and version-aware.

Seven asset types are supported. CMDB presentation uses cmdb_attribute_definition and cmdb_asset_type_attribute; canonical values remain typed. Migration 025 initially maps 18 fields to each type and preserves later custom mappings on rerun. See [CMDB attributes](cmdb-asset-type-attributes.md).

## One-command database setup

After `npm ci --offline`, run `npm run setup:database` under the Windows identity that will run the app. Interactive setup first asks `Is the SQL Server endpoint localhost\SQLEXPRESS? [Y/n]`. Yes/Enter selects local SQLEXPRESS; No asks for a nonempty endpoint such as `tcp:server,port` or `server\instance`. For local SQLEXPRESS, setup reads the instance's enabled TCP configuration and selects its configured static or assigned dynamic port when available, including a loopback-only listener. If inspection is unavailable, it retains the named endpoint. It never changes instance protocols or starts SQL Browser.

Interactive setup prepares **TSAATDB**, including when an existing DB_config names a different database. Enter a new database username (default `tsaat_app` or the previously saved SQL username), a hidden password and its confirmation. Then select the administrator connection: current Windows account by default, or a separate SQL administrator username/password. The administrator must be a SQL Server sysadmin; the application login receives no server roles. SQL Server must already allow SQL Server and Windows authentication (mixed mode). Setup does not install SQL Server, enable protocols, change authentication mode or restart services.

`setup:database` now explicitly disables SSL for the administrator/bootstrap connection and the saved application connection. There are no SSL/certificate questions in this workflow. DB_config remains encrypted at rest using Windows DPAPI; administrator credentials are never persisted. A server configured to force encryption can still require TLS; setup does not change server policy. Database Settings no longer exposes SSL/TLS controls or a separate SSL test button. It preserves saved transport values and includes any required encryption check in Test Connection. Configuration-only tools and compatibility APIs retain TLS support, including Strict. The CLI change supersedes the setup portion of [ADR 0016](adr/0016-complete-database-setup.md); see [ADR 0017](adr/0017-dedicated-database-login.md).

The endpoint and credential questions are shown on every interactive setup, even with an existing DB_config. Answer No to enter a different endpoint. If a named instance cannot be reached, enter its configured `tcp:server,port` endpoint. Check administrator credentials and mixed mode when connection/login preflight fails. Passwords follow the server's password policy; setup accepts up to 128 characters without line breaks or semicolons and trims surrounding whitespace, consistent with DB_config. Passwords are not printed or passed as process arguments.

For a missing database, setup confirms the target, creates it with a race-safe CREATE, applies the base schema and ordered migrations, streams local reference JSON and eight sample snapshots through the administrator connection, and populates the existing sample entity/CVE/patch details. No SQL Server file shares are needed. The data is bundled demonstration material. After schema validation, setup creates the login and matching database user in a transaction. The user receives `db_datareader`, `db_datawriter`, `EXECUTE` on the `tsaat` schema and `VIEW DEFINITION` in this database. It receives neither `db_owner` nor server administrator roles. Login creation enforces the server password policy, with password expiration disabled for this application account.

The final connection/schema/snapshot checks use the new application login; SSL diagnostics are skipped because SSL is disabled. Only after these checks succeed does setup save DPAPI-encrypted DB_config. Run `npm run dev:sql`, or `npm run build:sql` followed by `npm run start:sql` for a compiled app. Runtime SQL passwords are sent through the child process's `SQLCMDPASSWORD` environment. Failed SQL authentication no longer automatically retries as the Windows runtime account; the legacy fallback requires explicit `TSAAT_SQL_TRUSTED_FALLBACK=true`.

For an existing database, setup now **deletes and replaces it** after checking the administrator and application login. Interactive setup displays the server/database, explains that all data/settings will be lost and active sessions disconnected, and requires typing the exact database name. Enter, Yes, or another name cancels before deletion. No automatic backup is created; make your own backup before confirming if existing data is needed. Setup rechecks the observed database ID/creation timestamp before dropping it from a master connection, then invokes the guarded bootstrap against the now-missing name. System databases cannot be replaced. Other databases are untouched. This behavior is defined in [ADR 0018](adr/0018-replace-database-during-setup.md).

A setup-managed login is recognized by the `TSAAT_SETUP_LOGIN` property and matching SID in the old database. Setup verifies its password before deletion and carries that SID through the current run to reconnect the same login to the replacement database. It never resets login passwords, drops server logins, adopts unrelated logins or remaps conflicting database users. A different new username is also supported. Login/user changes are transactional, but dropping and rebuilding a database is not: a later failure cannot recover the removed data. Failed builds remain for inspection and DB_config is not overwritten. Restore your own backup to recover the old database. If a build failed before the preserved login was reattached, choose a new application username or have the administrator resolve the retained unmapped login before retrying.

Unattended setup requires `TSAAT_DB_CONFIG_ASSUME_YES=true`, `TSAAT_SQL_SERVER`, `TSAAT_SQL_USER` and `TSAAT_SQL_PASSWORD` for new configuration. `TSAAT_APP_DATABASE` defaults to TSAATDB; explicit alternate names support disposable validation. **Replacing an existing database additionally requires `TSAAT_DB_REPLACE_EXISTING` equal to the exact selected database name**; assume-yes alone cannot delete it. The administrator defaults to Windows authentication; supply both `TSAAT_SQL_ADMIN_USER` and `TSAAT_SQL_ADMIN_PASSWORD` for SQL administrator authentication. SSL is disabled by this workflow. An existing readable SQL/no-SSL DB_config takes precedence on reruns. Existing Windows/SSL configurations require an interactive run or an isolated `-- -DbConfigPath <path>`; unattended runs refuse to silently convert them. Use process environment variables for secrets. The app itself reads DB_config in its working directory.

The lower-level `npm run db:bootstrap -- -DatabaseName TSAAT_UI3_Dev` remains available with encrypted certificate-trust defaults and refuses an existing database. For strict validation, invoke the PowerShell script with `-TrustServerCertificate:$false`. It does not create an application login or save DB_config; use `setup:database` for the complete workflow. Direct `ensure-db-config.ps1` without `-SetupDatabase` remains configuration-only and retains its authentication/TLS options for compatibility.

Repository JSON is demo/test material, not an export of the running database. Database cleanup is validated using isolated restored/fresh databases; the original database is not implicitly rebuilt or migrated.

Fresh guarded bootstrap also applies the reviewed CVE inventory population after sample import. This is limited to the new disposable database and is separate from additive migration 028; existing/operational databases are never populated by an application build.

## Cleanup migration 027

The schema after migration 027 had 66 tables; migration 029 adds server_patch_observation. Migration 027 removes the unused KPI parameter table and synthetic hash function, eight retired calculation rows, three unused report-detail definitions and managed_network.apm_number. System APP-ID, active KPI definitions/tasking, hierarchy, snapshots, findings, settings and report reference URLs remain. See [cleanup audit](cleanup-audit.md) and [ADR 0004](adr/0004-retired-runtime-cleanup.md).

Apply only 027 to a database already through 026, using an explicit target, verified backup and sqlcmd -b. It refuses custom/retired KPI bindings that need review and is transactional/rerunnable. Never replay 001-026 on an upgraded database. The fresh bootstrap runs the entire historical chain followed by 027; it then imports only current reference data. Older app loaders require the removed network column, so use a separate restored database if the older app must continue running. Recovery restores the backup and matching old app together.

## Existing database upgrade

For Personas, apply additive migration 031 before deploying the new SQL application. It creates persona_settings_version without changing inventory, existing settings or calculations; Database Settings schema diagnostics check the new table and columns. Fresh loaders seed the shared `data/personas.json` catalogue; existing empty tables supply bootstrap defaults in memory. Payload version 3 adds stored names and dynamic IDs/order without DDL. Saves compare the current revision in a transaction before appending; stale saves return a conflict. Version-1/2 settings upgrade only on explicit save. See [Personas upgrade and recovery](personas.md).

For Security Vulnerability Explorer, apply additive migration 028 before deploying the new SQL application. It adds nullable `cve_name`, `cve_created_date`, `software_name`, `software_version` and `reference_url` to `asset_vulnerability`, retaining its key and all original observations. No rule/configuration or sample data is changed. The separate sample-only population script is explicitly opt-in and never part of a production migration. See [CVE mapping and SQL/JSON rollout](security-vulnerability-explorer.md).

Back up and verify restore. Compare deployed schema/configuration, select missing approved migrations in numeric order and run sqlcmd with `-b` against the explicit target. Retain execution evidence outside Git. Validate schema, references, settings, snapshots, KPI/SPI results and reports before release. Use the approved restore/recovery plan; no automatic down migrations or migration ledger are claimed.

Do not apply 026 to operational imports: its Sample metadata and example.test addresses are demonstration values, not verified contacts. Future migrations must state schema/config/demo scope, preconditions, row impact, idempotence and recovery. Review both fresh-install and upgrade paths.

Regenerate docs after SQL/reference changes and inspect ERD/mappings. Run validation SQL and integration suites on a disposable target. Keep deployed migration evidence and live schema comparisons with the release record.

## No-SQL build relationship

The same app also compiles with a JSON data provider. SQL implementation remains behind lib/data-loader.ts in lib/sql-data-loader.ts; CMDB SQL access similarly remains behind the shared attribute-loader facade. The setup/TLS changes add no schema or JSON format change, so no new SQL migration, JSON upgrade or calculation-contract checksum refresh is needed. Existing JSON stores are untouched.

No-SQL loads snapshots, references and settings from its own server directory. Initial seed JSON is sample material, not an export of this database. Existing SQL data is not accessed or mutated during builds. Explicit authorized read-only SQL exports can populate No-SQL snapshots through the backed-up import workflow; the source database is not modified. Imported values, dates, relationships and persisted findings are preserved, with only missing demonstration attributes enriched when --demo is selected. Runtime extracts stay outside Git. See [data-provider population and recovery](data-providers.md). SQL rule/schema changes require equivalent JSON calculations and regression review before updating NoSQL/calculation-contract.json. Per-type defaults are in NoSQL/cmdb-attributes.json; runtime overrides live in the store references directory.

Future schema changes require reviewed SQL migrations plus a JSON schema/data upgrade plan. Do not update only fresh-install seeds. See [data provider contracts](data-providers.md) for persistence, supported calculations and historical finding import requirements.

Known-endpoint sample coverage repair is a separate explicit No-SQL maintenance operation. It preserves SQL-exported history and appends labelled sample observations using existing configured evaluations. No SQL schema/data migration or certificate exception is involved; SQL findings generation and rule definitions remain unchanged. Recovery restores the selected complete JSON-store backup.


Migration 030_security_domains.sql adds managed-network security_domain, normalizes all three entity tables and enforces canonical domain values/defaults. Apply it after 029 using the selected database and trusted TLS; fresh schema/loader and SQL export mappings align. See [upgrade instructions and opt-in disposable parity](security-domains.md).
