## Business Reporting

The five personas are Analyst, Life Cycle Management, Configuration Management, DSOC Analyst and Business Reporting. Business Reporting uses the stable ID `business-reporting` and starts with every section, page and popup enabled, matching the other personas' defaults. Configure it in Menu → Settings → Personas; its selection appears in the header and is remembered in this browser.

Existing version-1 or version-2 settings containing exactly the original four personas load with Business Reporting added in memory. Existing selections, empty lists and revision timestamps are retained; the existing version-1 section-to-page upgrade still applies. Missing original personas, duplicates and invalid IDs remain errors. Configured Business Reporting selections, including empty lists, are never refilled.

Both providers retain their current storage format: SQL migration 031 and JSON store version 1/persona payload version 2. No additional SQL migration or bulk JSON migration is needed. Back up the selected database or JSON store, deploy the updated application to all instances and refresh existing browser tabs. Reads, setup and builds do not rewrite settings. The next explicit Save personas appends the complete five-persona SQL revision or atomically saves the five-persona JSON file/history. Writes containing only four personas are rejected with a reload message, preventing stale clients from resetting Business Reporting. For rollback to an application supporting only four personas, restore a compatible pre-upgrade settings revision or store backup with that application.

## Sections, pages and popup controls

Each persona maps to the current sidebar page catalogue and its six parent sections. A section checkbox selects or clears all its pages and shows a mixed state when only some are selected. Clearing the last page hides that section. Existing network/system scope rules still apply after these preferences. Show all/Hide all includes both page and popup switches; Save/Discard retains the existing draft behavior.

Installed Software Dashboard is hidden from the sidebar under every scope, including when its bookmarked URL is active. Its `discovery-software-insights` preference and route mapping are retained for existing settings/link compatibility; the sidebar omission does not change application access or grant the Governance preference. The separate Installed Software Insights briefing uses `governance-software-insights` directly below Cyber Terrain Insights in Governance. New/default configurations include both; existing saved version-2 selections remain unchanged. Enable the new Governance page explicitly in Settings > Personas when needed. Explorer evidence links respect the separate Explorer preference. No parser/persistence, SQL migration or JSON format upgrade is required.

Internal drill-through links use the same destination mapping as the sidebar, including Discovery views, KPI/SPI tabs, filtered links, compatibility routes and new-tab links. Unavailable destinations remain visible as dimmed, labelled disabled links with no href or action; keyboard, Ctrl-click and context-menu navigation cannot activate them. Filter, scope and snapshot parameters do not alter which page a link belongs to. Entity-detail URLs also require their popup switch. Directly entered URLs and APIs retain the login-free access model; these self-selected preferences are not an authorization boundary.

Popup switches are independent of sidebar pages. A hidden Findings page does not disable finding popups; their own switches do that. Settings, column filters, search selectors, loading dialogs, inline expanders and report downloads are not restricted. The configurable popup families are:

| Popup switch | Entry points |
| --- | --- |
| CMDB details | Device-name buttons, heatmaps and analyser device actions |
| Network details / ICT system details | Risk-profile explorer detail links and their destination dialogs |
| KPI / SPI scope details | Measure explorer network/system counts |
| Expanded risk trend chart | Expand chart on either risk profile |
| Service Impact Topology | Explore selection |
| Service impact findings & CIs | Summary tiles and graph finding-details button |
| Finding drill-through lists | SPI charts and ICT-system analyser finding actions |

| Asset compliance view | ICT-system analyser compliance action |
| Discovery tool asset details | Tool-name, gap-count and coverage-tool actions |

Disabled popup actions use native disabled buttons or guarded chart actions. Popup rendering is also gated, including nested dialogs and entity-detail URLs. Menu and Settings always remain available for recovery. Selection remains exclusively in Settings.

## Version 2 upgrade

Version-1 section-only payloads are accepted and upgraded in memory: enabled sections acquire all their current pages; hidden sections stay hidden; all popup switches start enabled to preserve previous behavior. Missing version-2 lists, duplicate IDs and unsupported IDs/versions are rejected. Empty lists stay empty. Section gates and page lists must both permit a page; popup lists are independent. New catalogue entries are not implicitly added to already saved version-2 lists.

No further SQL migration is needed: migration 031 stores versioned JSON and remains unchanged. JSON store schema stays at version 1; only the optional persona payload advances to version 2. Back up the database/store before deployment. Reads and builds never rewrite existing persona files or revisions. The next explicit Save publishes a complete version-2 revision through the same SQL append or JSON atomic-write/history flow. To roll back to a section-only application, restore a compatible pre-upgrade persona configuration with its matching app; do not feed version-2 settings to an older parser.

## Persistence and upgrades

`GET/PUT /api/settings/personas` uses `lib/data-loader.ts`. Both providers validate the five known personas and unique supported section/page/popup IDs. Reads accept the original four-persona catalogue as described above; writes require all five. Empty arrays are valid; version-1 payloads use the upgrade described above. Invalid updates return 400 before writing; unavailable/corrupt storage returns a sanitized 500. Responses are not cached. Whole-form saves are last-successful-save-wins; unsaved drafts survive refreshes of the shared configuration.

SQL requires the additive [migration 031](../Database%20Schema/migrations/031_persona_navigation_settings.sql), applied after the installation's approved preceding migrations. Back up the explicitly chosen database, apply only this missing migration with `sqlcmd -b` and normal strict TLS, then deploy the app. It creates `tsaat.persona_settings_version` with an identity revision ID, JSON payload and UTC creation timestamp. Saves append one complete revision; reads choose the latest revision ID. An empty table supplies all-enabled defaults. Rerunning 031 retains all revisions. Fresh database loaders already apply ordered migrations after the base schema. Never apply the base schema or seed loader to an operational database. Until 031 is applied, the UI shows a load/save error with retry; ordinary navigation remains usable.

No-SQL retains store schema version 1. `settings/personas.json` is an optional additive file: a valid old or new store without the file reads all-enabled defaults without any write. The first explicit Save creates it using the existing writer lock, atomic replacement and a prior history revision under `settings/history/personas-*.json`. No bulk migration, initialization overwrite, reference replacement or snapshot rewrite is needed. Existing files must validate; corrupt/unknown formats are never silently reset. Builds and setup leave existing stores untouched.

Back up the complete SQL database or JSON store before deployment. For JSON recovery, stop writers and restore `settings/personas.json` from a validated compatible history revision or complete store backup, following [store recovery](data-providers.md). Preserve SQL revisions; restore a known configuration through Settings or restore the database backup with its matching app. Active persona can be reset by choosing All sections; it is not part of the server backup.

No SPI/KPI definitions, calculations, scope queries, CMDB mappings or calculation-contract checksums change. The base schema checksum remains unchanged because 031 is a separate forward migration.
