TSAAT Database Schema Description
================================

Overview
--------
The TSAAT schema (`tsaat`) stores snapshot-based cyber posture data for:
- managed networks and hierarchy
- ICT systems and hierarchy
- assets, environments, vulnerabilities, and findings
- discovery/measures/reference settings
- CI-to-CI dependency graph data used by topology views

Connection/bootstrap notes
--------------------------
- Runtime DB connection settings are stored in local repository root `DB_config` as an encrypted JSON envelope.
- The encrypted payload stores:
  - `server`
  - `database`
  - `authMode` (`trusted` or `sql`)
  - `userId`
  - `password`
  - `sslEnabled`
  - `sslType` (`strict` or `trust-server-certificate`)
- `DB_config` is app-managed via `/settings` or confirmed/created/recreated by offline scripts before database build/compile, is ignored by git, and should not be edited manually.
- Application login credentials are stored outside SQL Server in local repository root `logindetails` as an encrypted DPAPI CurrentUser envelope.
- The encrypted `logindetails` payload stores username, salted PBKDF2-HMAC-SHA256 hash metadata, and session-version metadata.

Snapshot model
--------------
- Core domain tables are keyed by `snapshot_id`.
- This preserves historical state per snapshot and supports timeline analysis.

  - stores severity, priority, and workflow grouping semantics used by finding analytics and UI summaries.
- `finding_evidence_field_definition`
  - stores supported evidence display mappings and fallback labels.
- `finding_register_column_definition`
  - stores supported register/export column labels, order, and value keys.

Data integrity highlights
-------------------------
- Enum-like values are enforced via `CHECK` constraints or reference tables where the application needs data-driven runtime options.
- Snapshot-aware foreign keys preserve cross-table referential integrity.
- SPI definitions are database-driven. `spi_definition` stores display order, default severity, enabled/report flags, catalogue `rule_key`, and report detail key; related SPI tables store applicability, typed rule parameters, tasking contacts, tasking action templates, tasking condition templates, feature bindings, and report configuration.
- SPI rule catalogues are database-driven. `spi_rule_definition` stores supported rule keys, `spi_rule_parameter_definition` stores parameter schemas/defaults, `spi_rule_outcome_template` stores reason/evidence templates, `spi_report_detail_definition` stores report detail keys, and `spi_finding_classification_rule` controls generated finding severity/priority using approved condition keys.
- SPI calculations are SQL-driven. `spi_calculation_source`, `spi_calculation_definition`, and `spi_calculation_evidence_expression` store constrained read-only SQL expressions evaluated by `usp_evaluate_spi_snapshot` against `vw_spi_asset_evaluation_context`; arbitrary batches, JavaScript, and unrestricted formula execution are not supported.
- KPI definitions and calculations are SQL-driven. `kpi_definition` stores catalogue metadata and visibility; `kpi_calculation_source`, `kpi_calculation_definition`, and `kpi_calculation_parameter` store constrained SQL-backed calculation metadata evaluated by `usp_evaluate_kpi_snapshot`; `kpi_report_detail_definition`, `kpi_report_detail_binding`, `kpi_tasking_team`, `kpi_tasking_action_template`, and `kpi_tasking_condition_template` store report and tasking metadata.
- Discovery coverage is SQL-driven. `discovery_coverage_source`, `discovery_tool_detection_definition`, `discovery_tool_detection_rule`, and `discovery_tool_detection_rule_value` store approved detection rules evaluated by `usp_evaluate_discovery_coverage_snapshot`; discovery tool scope remains editable through `discovery_tool` and `discovery_tool_asset_scope`.
- Finding features are database-driven. `vw_persisted_finding_normalized`, `usp_generate_spi_findings_snapshot`, `usp_get_effective_findings_snapshot`, `usp_get_finding_history_snapshot`, and `usp_get_finding_spi_history_snapshot` move persisted/generated effective finding selection, deterministic generated fallback, as-of status reconstruction, and history aggregation into SQL Server while the app remains the renderer/export serializer.
- `ci_dependency` enforces:
  - valid snapshot + asset references
  - no self-referential edge (`source_asset_id <> target_asset_id`)
  - valid dependency type
  - optional port bounds (1..65535)
