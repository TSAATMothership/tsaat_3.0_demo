# Repository working instructions

- Start with README.md, docs/README.md and the relevant feature specification.
- Before choosing checks, assess the actual change: UI/runtime behavior, SQL/JSON data and structures, calculations, scope/authentication, documentation/inventories, dependencies/builds and release risk. Use docs/sdlc.md. Record checks selected and why other categories are not applicable; reassess if scope grows. Do not automatically run the full suite for every change.
- Preserve header scope, selected snapshot dates, configurable measure definitions, the current application access model and compatibility routes.
- Update meaningful tests and feature/design/architecture/data documentation only where the change affects them. Record user-visible changes in CHANGELOG.md. If documentation is unaffected, do not force documentation edits, docs:generate or docs:check; record the reason in the change summary or PR.
- Support both compilation paths: SQL and JSON-backed No-SQL. Use lib/data-loader.ts and lib/cmdb-attribute-loader.ts; do not bypass them from feature code. Read docs/data-providers.md when data/provider behavior is affected. Compatibility remains required even when provider checks are not needed for a presentation-only change.
- For data, query, rule, schema, persistence or mapping changes, review both providers and NoSQL/calculation-contract.json. Run relevant provider/regression tests, storage:check, both builds and the compiled No-SQL smoke, plus applicable SQL parity checks using an explicitly selected disposable database. Never refresh checksums without reviewing behavior and regression evidence. Provide SQL migrations and JSON upgrade instructions where needed; never overwrite existing JSON stores during a build.
- For scoped application changes, use lint/type checking, focused tests and relevant browser/keyboard/report checks. For tooling changes, test the affected tooling. Run docs:generate only when generated inventories need refreshing; run docs:check when documentation or its inventories are affected. npm run check remains an explicit comprehensive gate, not the default for every edit. Broaden checks for shared/security-sensitive behavior, uncertain impact or failures; fix failures rather than disabling checks or adding blanket casts.
- Never apply database-schema.sql or seed loaders to an operational database. Add forward migrations; do not rewrite published migration files. New SQL settings default to SSL/TLS with Trust Server Certificate per ADR 0016; preserve explicit saved policies and the Strict option, with no automatic TLS downgrade.
- Offline installation and both compilations remain product/release requirements. Read docs/offline-builds.md for dependency, build or release work. All required packages/assets must be in the repository; no registry/cache/network fallback, remote fonts, lifecycle downloads or fetched generated code. Keep package-lock.json, vendor/npm archives and provenance/integrity aligned. Require offline:check, fresh empty-cache npm ci --offline and both guarded builds for dependency/build changes and release validation, not unrelated routine edits.
- Never commit DB_config, logindetails, .env files, installed node_modules, host runtimes, build outputs, logs or NoSQL/data. Only reviewed, lockfile-pinned vendor/npm archives are permitted dependencies (ADR 0007 supersedes that part of ADR 0002). There is no standalone Demo folder or generated-build exception. npm ci remains the installation contract; lifecycle scripts are disabled.
- Use FindingsDataTable, WorkspaceTabs, native modal patterns and app/globals.css conventions. Preserve keyboard support, focus return, narrow layouts and loading/error/empty states.
- Document significant decisions in docs/adr. Keep validation claims tied to actual checks and avoid unrelated cleanup.
