# Settings

Personas provides an Active persona selector for Analyst, Life Cycle Management, Configuration Management, DSOC Analyst and Business Reporting, and displays only the selected persona's configuration. Each editor has section/page checkboxes, independent popup switches and Show all/Hide all. Section checkboxes select all their pages and show a mixed state for partial selection. Switching personas retains pending edits; Save personas and Discard changes apply across all edited personas. All sections (no persona) shows an explanation with no configuration editor. Menu → Settings → Personas is the only place to select and configure personas; a read-only label immediately to the left of the header Security Domain filter shows the active selection. Shared saved configurations filter sidebar pages, disable navigation to unavailable destinations and disable separately selected popup actions; active persona is remembered per browser. Menu and Settings remain accessible with everything hidden. Direct URLs/APIs retain the login-free access model. See [Personas behavior, upgrade and validation](../docs/personas.md): migration 031 remains sufficient for SQL, and version-1 persona payloads upgrade to version 2 on the next explicit save.

Current contract: TSAAT UI 3 baseline, 2026-11-02. Maintain with related source changes; see [SDLC](../docs/sdlc.md).

The Personas editor uses section/Popup tabs with a compact permission grid and keeps Save/Discard visible. On narrow screens a group selector and three-item Previous/Next pages replace the tabs and long lists. All controls remain reachable without vertical scrolling at normal desktop, laptop and phone sizes; group/page changes retain edits and section checkboxes still select all child pages. The expanded, compact dialog layout applies only while Personas is selected. Natural overflow remains available for exceptionally short windows or enlarged text.

Menu → Settings opens a native modal above the workspace. Settings sizing is shared by expanded charts and the asset compliance view. Close/Escape returns to the workspace; local tabs do not discard its applied scope/date.

SPI Risk Matrix and SPI Priority Matrix are sibling tabs. Risk mapping is by configured SPI and canonical asset type; priority mapping is by SPI and configured priority rank. Saved settings are persisted in versioned SQL settings tables and influence subsequent app evaluation through version-aware cache signatures. They are not presentation-only selections. Discovery Tool settings define source metadata, ownership and per-type applicability.

Database Settings reads/writes encrypted DB_config and shows authentication, server, database, username/password, connection/schema tests and diagnostics. It has no SSL/TLS checkbox, certificate-mode selector or separate Test SSL button. The form carries the saved connection policy through tests, reset and save unchanged. If that policy uses TLS, Test Connection automatically includes the existing encryption validation; failure blocks schema testing and save. Fields are disabled while validation/save is running. Server-side save validation remains mandatory. Application Password Settings is retired; old settingsTab=password-settings links fall back to the storage tab. Masked or unchanged secrets must not be accidentally overwritten with placeholders. Diagnostics must not disclose passwords.

Interactive `npm run setup:database` asks whether the endpoint is `localhost\SQLEXPRESS`, asking for a custom endpoint after No. Yes uses the locally configured TCP port when discoverable. It prepares **TSAATDB**, asks for a database username and hidden password with confirmation, and creates a dedicated SQL login/user using a separate administrator connection. The administrator can use Windows authentication or separate SQL credentials; administrator credentials are never saved. Setup and the resulting app configuration use SQL authentication with SSL disabled, with no authentication-mode or TLS questions for the app connection. This explicitly replaces older saved authentication/TLS choices on a successful interactive run. If the database exists, setup displays its server/name and requires the exact database name before deleting all its data/settings, disconnecting sessions and rebuilding it. No backup is created. Missing and replacement databases receive schema/migrations/reference/sample data and database read/write/execute permissions without server roles. Only successful validation saves encrypted configuration. A verified setup-managed login can be reattached using its original SID/password; unrelated logins and password resets are refused. Unattended replacement requires `TSAAT_DB_REPLACE_EXISTING` equal to the selected target name; assume-yes alone is insufficient. See [database setup and recovery](../docs/database.md#one-command-database-setup).

Settings does not authorize destructive schema rebuilds or demo imports. Source: components/settings-popup.tsx, settings-tabs.tsx, spi-risk-settings-popup.tsx and settings forms; lib/measures-settings.ts, discovery-tools-settings.ts, db-config.ts and related APIs. Tests cover priority/risk settings behavior, password handling, SQL TLS, DB config and retired-login compatibility. Verify save/reopen and subsequent scoped results, not just successful toast text.

Database schema diagnostics include persona_settings_version and its columns after migration 031; they no longer require the unused KPI parameter table or network apm_number. Risk/priority settings and version tables are retained.

An empty persona settings table in a freshly created SQL database loads the default persona configuration without requiring an initial manual save, matching the JSON provider.

## SQL and No-SQL build settings

Both builds use the same Settings dialog, SPI risk/priority matrices and discovery applicability editor. SQL retains Database Settings with the saved transport policy handled internally. No-SQL replaces that tab with JSON Data Files, showing the configured server directory and available snapshots; SQL configuration/test APIs return 409 in that build.

No-SQL saves settings to JSON files on the server, using atomic replacement and a writer lock. Changes affect subsequent calculations, are shared by browser sessions and survive app restarts. Initialization and recompilation retain existing settings. Verify save/reopen, changed findings and restart persistence using the compiled No-SQL smoke. See [storage contracts](../docs/data-providers.md).
